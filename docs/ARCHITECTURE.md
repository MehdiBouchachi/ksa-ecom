# Architecture & hosting — single app + PostgreSQL (NOT Supabase)
- **Repo:** pnpm monorepo. `apps/web` = only deployed Next.js App Router application (public store, customer account, admin + backend Route Handlers/Server Actions). Optional `packages/contracts`, `db/schema`, `db/migrations`, `tests`, `docs`. No separate backend runtime.
- **Server modules:** `apps/web/src/server/{db,auth,catalog,pricing,inventory,orders,payments,shipping,notifications}`; `src/app/{(store),(auth),account,admin,api}`. React Server Components default; Client Components only for interactivity. Services called from both Server Actions and HTTP routes; never implement business rules twice.
- **Database:** PostgreSQL accessed through **Drizzle ORM + `pg`/node-postgres** (`drizzle-orm/node-postgres`, `drizzle-kit`); schema/migrations committed. Use PostgreSQL types, constraints, unique indexes, `timestamptz`, JSONB when useful. Use parameterized queries, explicit DB transactions and row locks. Migrate through a controlled job/CLI, never automatically on a public page request.
- **Deployment topology (Business/Unlimited):** Hostinger serves the **single Node/Next.js application**. PostgreSQL is **external managed PostgreSQL, not Supabase**; this is a separate DB service/cost, but not a second app deployment. Keep `DATABASE_URL` **server-only**, enable **properly verified TLS/SSL** and choose provider/region/connection pool appropriate to production traffic. Test outbound connections from Hostinger, IPv4/IPv6 support, connection limits, latency, and deployment connectivity before accepting the host/provider combination. Avoid `ssl: { rejectUnauthorized: false }` as a blanket fix.
- **Alternative only if hosting plan changes:** Hostinger VPS can run both Next.js and PostgreSQL on the same server, but is NOT the Business/Unlimited managed hosting plan and requires OS/database backups, patching, and secure network setup. Do not silently migrate plans.
- **Auth:** Auth.js Credentials with secure HttpOnly cookies/JWT-session strategy; user credentials, password hashes and reset tokens in PostgreSQL. Recheck current user role/account status in DB on protected operations, throttle logins, validate CSRF/origin for browser mutations. Hash with maintained library compatible with Hostinger runtime. Never trust roles stored solely in client JWT.
- **Authorization:** backend RBAC and owner-scoped queries (`user_id = authenticatedUser.id`) for customer resources. Manager sees order-specific shipping contact only, no user/customer directories; Admin manages administrative users. PostgreSQL RLS is **not required** for this server-only application; if added, policies/session context must be designed and tested separately rather than assumed.
- **Media:** deploying to Hostinger can replace app directories; never put durable user-uploaded media inside `.next`/`public_html`. Use merchant-approved storage (e.g. R2) or a tested persistent path independent of deployments; signed upload and file validation.
- **Hostinger limits:** Business/Unlimited supports Next.js Node deployment but no custom always-running services, Redis, Docker or perpetual workers. Use bounded, authenticated/signed cron HTTP endpoints for PSP reconciliation, reservation expiration, Aramex polling, email outbox; ensure idempotency and database-backed deduplication.
- **CI/ops:** lint/typecheck/unit/build, **integration tests against actual PostgreSQL** (container in CI/local acceptable, not on Business production), and real PostgreSQL concurrency tests. Staging/prod separation; DB backups, restore drill and rollback procedures. Validate Hostinger monorepo build settings; if pnpm workspace autodetection fails, deploy app artifact from same repo without adding another runtime.
- **Performance:** public catalog pages SSR/SSG/ISR as appropriate, page metadata, sitemap, optimized images, caching of non-personal content only; never treat cached stock/checkout pricing as authoritative. Index owner/order/status/variant fields; small connection pools and no N+1.
